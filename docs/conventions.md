# 코드 작성 규칙과 팀 합의

Claude는 코드를 만들거나 고칠 때 이 문서를 따른다. 1장은 정해진 규칙이고, 2장은 회의에서 정할 항목이다. 2장의 **[결정 필요]** 항목은 정해지기 전까지 임의로 정하지 않고, 필요하면 사용자에게 묻는다.

## 1. 정해진 규칙

### 언어와 이름

- 코드의 이름(변수, 함수, 파일)은 영어로 쓴다. 주석, 커밋 메시지, PR, 화면 문구는 한국어로 쓴다
- 파일·폴더 이름은 영어 소문자-하이픈: `slot-card.tsx`, `reservation-list/`
- React 컴포넌트는 PascalCase(`SlotCard`), 함수·변수는 camelCase(`getNearbySlots`), 상수는 UPPER_SNAKE_CASE(`MIN_DISCOUNT_RATE`)
- DB 테이블·컬럼은 snake_case(`start_at`), 코드에서는 camelCase(`startAt`)로 쓴다. 변환은 Drizzle 설정으로 한다
- 커밋 메시지와 PR 제목에 기능 ID를 넣는다: `feat: C-202 매물 카드 추가`

### 화면과 서버 코드 (Next.js)

- 기본은 서버 컴포넌트다. 상태, 클릭 이벤트, 위치, 지도처럼 브라우저 기능이 필요할 때만 `'use client'`를 쓴다
- 데이터 저장·변경은 Server Action으로 만든다. 한 화면에서만 쓰면 그 화면 폴더의 `actions.ts`에, 여러 영역이 같이 쓰면 `src/server/`에 둔다
- 서버로 들어오는 모든 입력은 zod로 검증한다
- 서버 함수의 결과 형태를 통일한다: 성공은 `{ ok: true, data }`, 실패는 `{ ok: false, error: { code, message } }`. 화면은 `message`를 사용자에게 보여준다
- 목록·상세 화면은 **로딩 중, 데이터 없음, 오류** 세 상태를 모두 만든다
- 이미지는 `next/image`로 표시한다
- 공통 UI(`src/components/ui/`)에 있는 컴포넌트를 먼저 쓴다. 없으면 만들기 전에 사용자에게 알린다(공통 UI는 현동훈 담당)

### 화면 문구와 디자인

- 화면에 보이는 문구는 해요체로 쓴다: "예약이 완료됐어요", "매물을 등록해 주세요". 버튼은 짧은 동사형("예약하기", "등록")
- 이용약관, 개인정보 처리방침, 환불 규정 전문 같은 법적 문서는 격식체(합니다체)로 쓴다
- 고객·업주 화면 모두 판매 단위를 "매물"이라고 쓰고, 업주는 "원장님"으로 부른다
- 라이트 모드만 지원한다. 배경은 흰색 위주로 하고, 다크 모드 스타일(`dark:`)은 만들지 않는다
- 서비스 이름은 바뀔 수 있다. 화면에 '줍줍'을 직접 쓰지 않고 공통 설정값(`src/lib/site.ts`의 서비스 이름 상수, 뼈대에서 만든다)을 가져다 쓴다
- 브랜드 색·글꼴은 아직 정하지 않았다. 색은 공통 UI의 색 이름(테마 토큰, 예: `bg-primary`)만 쓰고, 색 코드(`#3B82F6`)를 화면 코드에 직접 쓰지 않는다. 정해지면 한 곳만 바꾼다

### 돈, 시간, 정책

- 금액은 원 단위 정수. 할인가는 원 미만을 버린 뒤 100원 단위로 올림. 수수료와 그 VAT는 원 미만만 버림. 계산은 정책 함수로만 한다
- 시간은 DB에 UTC로 저장하고, 화면에는 한국 시간으로 보여준다. 시간 계산은 공용 함수로만 한다
- 서버에서 "지금"이 필요하면 `getRequestNow()`(`src/lib/request-time.ts`)를 쓰고, 그 컴포넌트는 `<Suspense>` 안에 둔다. 화면의 남은 시간은 이 값을 `serverNow`로 받아 `Countdown`으로 보여준다
- 정책 숫자(48시간 게시, 위약금 구간과 비율, 6시간 임박, 10분 홀딩, 할인율 선택지, 할인율별 수수료율, 업주 귀책 보상·패널티 금액 등)는 `src/server/policy/`에서 가져다 쓴다. 문구 안의 숫자("6시간 이내 환불 불가")도 정책 값으로 만든다
- 매물 상태 이름은 예약대기·게시중·예약됨·마감·취소·완료 6개만 쓴다

### 보안과 개인정보

- 권한은 서버에서 확인한다. 브라우저에서 온 가격·금액·사용자 ID는 믿지 않는다
- 비밀 값에는 `NEXT_PUBLIC_`을 붙이지 않는다
- `console.log`에 개인정보(연락처, 계좌번호, 이메일)나 키를 남기지 않는다. 디버그 로그는 PR 전에 지운다

### 품질

- PR을 올리기 전에 자동 검사를 통과시킨다: `npm run format` → `npm run lint` → `npm run typecheck` → `npm test` → `npm run build`. 같은 검사가 PR마다 GitHub Actions(`.github/workflows/ci.yml`)에서도 돌고, 통과해야 머지된다
- 정책·돈·시간 계산 함수는 테스트를 같이 만든다. 테스트 파일은 코드 옆에 `이름.test.ts`로 둔다(예: `src/lib/time.test.ts`)
- 시간 계산은 `src/lib/time.ts`, 서버 함수 결과는 `src/lib/result.ts`의 `ok()`·`fail()`, 클래스 합치기는 `src/lib/utils.ts`의 `cn()`을 쓴다
- 코드 모양(따옴표, 줄바꿈, Tailwind 클래스 순서)은 Prettier가 정한다. 손으로 맞추지 않는다
- 화면은 직접 열어서 확인한다. 고객 화면은 폰 크기(폭 375px), 업주 화면은 PC와 폰 크기 둘 다, 운영자 화면은 PC 크기로 확인한다
- 새 npm 패키지는 설치 전에 사용자에게 묻는다

### 완료의 기준

PR을 올릴 수 있는 상태는 아래를 모두 만족할 때다.

1. 기능 명세의 상세 내용을 빠짐없이 구현했다(못 한 부분은 PR에 적는다)
2. 자동 검사를 통과했다
3. 화면을 직접 확인했고, 로딩·빈 상태·오류 상태도 확인했다
4. 담당 폴더 밖을 고치지 않았다(고쳤다면 이유를 적었다)
5. 사용자가 PR 내용을 자기 말로 설명할 수 있다
